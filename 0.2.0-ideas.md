# Ideas deferred to 0.2.0

Things considered while building a feature for the current release, but
deliberately not built now.

## Pattern matching for `route-map` routes

Today (v0.1.x) a `route-map` route's `match` is compared against argv
tokens with an exact string match only -- identical semantics to
`route-args`' own trigger matching, just generalized to N routes instead
of one. E.g. `match = "--v8"` only fires on a literal `--v8` token.

A natural extension is prefix or glob matching, e.g. `match = "--v*"` or
`match = "--v8*"`, so a shim could route on a whole family of flags
without one route per exact value.

This was deferred rather than built alongside the initial `route-map`
implementation because it opens real ambiguity questions that need their
own design pass, not just an implementation:

- **Overlapping prefixes.** If both `--v8` and `--v*` are configured as
  routes, which one fires for an argv token of `--v8`? The literal, more
  specific one? Or whichever route appears first in the list?
- **Match-order sensitivity.** Once matches aren't exact strings,
  route order stops being cosmetic -- two glob routes could both match
  the same token, and which one "wins" needs a documented, tested rule
  (first match in declaration order? most specific pattern? longest
  match?), not just whatever the implementation happens to do.
- **Validation implications.** The current duplicate-route check compares
  `(command, args)` tuples exactly; it's unclear whether two routes with
  overlapping *patterns* but different commands should also be flagged
  at `add`/validation time as a likely mistake, and if so, how to detect
  "overlapping" for arbitrary glob patterns without over-engineering it.

Worth a proper design pass (and its own plan) before implementation,
rather than bolting it onto the exact-match version.
